Local-first repository map for engineers and coding agents

Know what a change touches, and why.

ArchMap scans a Git repository into a reviewable architecture model. Relations carry evidence: the source path, a content hash, the analyzer, and the commit it was read at (or working-tree for uncommitted content). Status reports which nodes went stale when their code changed. The CLI, MCP tools, and viewer all read that same model.

Three questions it answers from source

  1. What does this file affect?

    archmap impact walks reverse dependencies: the modules that scope the changed files, and every module that imports them directly or transitively, each with the reason it was included.

  2. Why should I believe that?

    archmap evidence returns the path, symbol, blob hash, analyzer, and commit (or working-tree) behind a node or relation. Heuristic findings are labelled partial, not presented as fact.

  3. Is the map still current?

    archmap status compares the working tree with the last snapshot and names the stale nodes. archmap scan brings them back in line.

        How it works

        Scan

        archmap scan walks the Git working tree, skips excluded directories and secret-looking files, and runs deterministic analyzers: TypeScript and JavaScript via the compiler's syntax parser, Python, Markdown, and data/config files. It writes .archmap/snapshot.yaml and one YAML file per node. Scanning an unchanged tree produces no diff, so the model can be committed and reviewed like code.

        Query

        context, impact, evidence, search, and work-items read the tracked model. The same queries are exposed to coding agents over MCP (archmap mcp). AI can only add interpretations through validated, evidence-backed proposals; scanner facts and human decisions stay separate.

        Stay current

        The snapshot records a content hash per file. archmap status diffs the live tree against it and marks the nodes that scope changed files as stale; archmap check can gate CI on it.

        Limits worth knowing

        • The graph is static and syntactic. There is no type resolution and no runtime tracing. In the sample, src/plugins/load.ts imports modules by a computed name, so no edge is recorded for them.
        • Routes, HTTP calls, and CLI commands are detected heuristically and recorded as partial. Imports that cannot be resolved inside the repository are partial too.
        • The built-in viewer lays out at most 60 nodes and 120 edges. Larger repositories need a named view that narrows the graph by path prefix or node kind.
        • One real-repository pilot has been completed. That is not a claim that every framework or repository shape is supported.

        Run it from source

        ArchMap is not published to npm. Clone the repository and build it with Node.js 20 or newer and Git.

        Reproduce this example

        git clone https://github.com/xxxxxthhh/archmap.git
cd archmap
npm ci
npm run build
npm run demo

        npm run demo copies examples/lending-desk into a new temporary directory, runs the loop shown above, and deletes that directory afterwards. It never touches the checked-in sample or any other path.

        Map your own repository

        cd /path/to/your-repo
node /path/to/archmap/dist/cli/bin.js init
node /path/to/archmap/dist/cli/bin.js scan
node /path/to/archmap/dist/cli/bin.js impact src/some/file.ts

        ArchMap works on the Git repository that contains your current directory, so run it from inside the repository you want to map. init creates .archmap/ at that repository's top level.

        Details: docs/quickstart.md and docs/flagship-demo.md in the repository.
